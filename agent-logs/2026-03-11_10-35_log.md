1. **`STEPControl_Reader`** (highest risk):
   - File I/O operations
   - Global resource caching
   - Internal static state for entities

2. **`RWStl::ReadFile`** (read_file_charptr_progressrange_2):
   - File I/O
   - Polygon triangulation caching

3. **`Interface::Static`** (set_c_val):
   - EXPLICITLY global/static configuration
   - Shared across all OCCT operations

4. **Message::Messenger** (default_messenger):
   - Global singleton managing output/error streams
   - Modified in `suppress_occt_messages()`

5. **GeomAPI operations** (IntSS, ProjectPointOnSurf):
   - May use cached geometric results
   - Surface-surface intersection has complex internal state

### Why Stage 2 Crashes with Multiple Tests

The parallel test runner (`cargo test --test stage2_integration`) spawns multiple test threads:
- Each test calls `config_for_compare()` which calls `config.load_compare_step()`
- This uses `step_control::Reader` simultaneously in multiple threads
- OCCT's `Reader` is **not thread-safe** - its internal state (entity caches, model handle) is unprotected
- **Race condition**: Two threads reading different STEP files can corrupt each other's internal state
- Result: segfault in TKernel or TKSTEPBase layer

### Key Findings

| Finding | Evidence |
|---------|----------|
| **OCCT is single-threaded** | C++ standard library circa 2020+, plus OCCT's age (pre-C++11 threading) |
| **No global mutex exists** | Zero synchronization in brepper; opencascade-sys bindings are thin FFI wrappers |
| **`STEPControl_Reader` is unsafe** | Crashes occur ONLY during multi-threaded `load_compare_step()` |
| **Messenger is shared state** | `suppress_occt_messages()` modifies global messenger that all threads access |

| **`Interface::Static::set_c_val()` is global** | Sets process-wide STEP metadata visible to all threads |

### Conclusion

**OCCT is fundamentally single-threaded.** The library was designed with:
- Global state (Messenger, Static settings, cached entities)
- No thread synchronization (no mutexes in the C++ source)
- Assumptions that operations complete synchronously without interruption

The correct solution is to **serialize all OCCT access** with a global Mutex, ensuring at most one thread executes OCCT code at a time.
