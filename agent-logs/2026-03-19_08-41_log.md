### The BFS Abstraction Mechanism

The abstraction uses **C++ static polymorphism via a traits pattern** — not virtual functions, not CRTP, just a plain struct with static methods that a function template calls by name. The single generic function is:

```cpp
template <typename Traits>
static void generate_hypotheses(
    ConnectedMesh& mesh,
    const Stage2Config& config,
    std::vector<typename Traits::Hypothesis>& hypotheses);
```

This ~200-line template function ([stage2.cpp](src/stage2.cpp) lines ~870–1190) implements the **entire BFS loop** once, parameterized by `Traits`.

### Per-Surface-Type Implementations

#### `PlanarTraits`
- **Fit type**: `PlanarFit` (normal + distance)
- **Seeds**: Single face (`{fi}`) — simplest possible seed
- **Fitting**: Area-weighted normal averaging + mean vertex distance
- **Distance**: `|n·p - d|` (signed plane distance)
- **Convexity**: Always `true` (no convexity concept for planes)
- **Acceptance**: ≥ 2 faces

#### `ConicalTraits` (cone + cylinder combined)
- **Fit type**: `ConicalFit` (apex, axis, half_angle, radius, convex) — **single struct for both**
- **Seeds**: **3-face seeds** — `fi` + two non-mutual-neighbor qualified neighbors with sufficiently different normals (`cross(n_i, n_j).norm() ≥ 0.01`), checked against angular tolerance
- **Fitting**: Tries **both** `fit_cylinder_direct()` and `fit_cone_direct()`, computes max vertex error for each, picks the one with lower max error. This is the key cone+cylinder combination mechanism.
- **Distance**: Dispatches on `fit.half_angle < 1e-4` → cylinder distance vs cone distance
- **Convexity**: Normal dot radial direction (away from axis = convex)
- **Acceptance**: ≥ 3 faces + angular coverage validation (computes face centroid azimuthal angles around axis, requires span ≥ 0.1 rad, largest gap reasonable)

#### `SphericalTraits`
- **Fit type**: `SphericalFitInternal` (center, radius, convex)
- **Seeds**: 1-ring vertex neighborhood of `fi` (all faces sharing a vertex with `fi`) — produces larger seeds because sphere fitting needs more geometric diversity
- **Fitting**: Calls `fit_sphere()` with `max_radius = 1000 × bbox_diagonal`
- **Distance**: `| ||p - center|| - radius |`
- **Convexity**: Normal dot direction-from-center
- **Acceptance**: ≥ 4 faces + **solid angle coverage** — computes covariance of unit directions from center to centroids, requires `λ_min / λ_max ≥ 0.01` (3D spread, rejects fillet-like strips)
- **Extra**: Builds `vertex_to_faces` map before BFS, clears it after

#### `ToroidalTraits`
- **Fit type**: `ToroidalFitInternal` (center, axis, major_radius, minor_radius, convex)
- **Seeds**: 1-ring vertex neighborhood, requires ≥ 7 faces and ≥ 9 unique vertices (torus fitting is data-hungry)
- **Fitting**: Calls `fit_torus()` — PCA for axis, Kasa for center, linearized circle fit for radii, Gauss-Newton refinement
- **Distance**: `| sqrt((ρ - R)² + h²) - r |`
- **Convexity**: Computes tube center at each face's azimuth, checks normal vs direction from tube center
- **Acceptance**: ≥ 7 faces + angular coverage around the **minor circle** (tube cross-section), not the major circle
- **Extra**: Also builds/clears `vertex_to_faces` map

### How Cone + Cylinder Are Combined

This is the most interesting design choice. Rather than separate BFS passes:

1. **Single `ConicalTraits` struct** handles both — `ConicalFit` has `half_angle` (0 = cylinder) and `radius` (0 = cone)
2. **Single hypothesis field** on `MeshFace`: `conical_hypothesis` (not separate `cylindrical_hypothesis` and `conical_hypothesis`)
3. **`fit_surface()` tries both fits every time** and picks the better one by max vertex error
4. **`vertex_distance()` dispatches** based on `half_angle < 1e-4`
5. At the **hypothesis output level**, `ConicalHypothesis::is_cylinder()` distinguishes them
6. At **surface selection** (stage 2.5), cylinders get `SurfaceType::Cylindrical`, cones get `SurfaceType::Conical`

This means a BFS region that starts looking cylindrical can **transition to conical** if a refit finds a cone fits better (or vice versa), because every refit re-evaluates both interpretations.

### Key Algorithmic Features of the Generic BFS

The `generate_hypotheses<Traits>()` template implements several cross-cutting concerns:

1. **Bootstrapping mode**: When seed vertices fail vertex tolerance (e.g., sphere/torus seeds are too large initially), the BFS switches to "bootstrapping" — accepts faces based on angular tolerance only, then validates the entire region after BFS completes with a final refit. This handles the chicken-and-egg problem where you need many points to fit well, but can't validate individual faces without a good fit.

2. **Three-tier acceptance during BFS expansion**:
   - **Direct accept**: vertex distance ≤ `vtol` AND centroid distance ≤ `stol`
   - **Skip (too far)**: vertex distance > `skip_vtol` OR centroid distance > `skip_stol` (where `skip_*tol = tol × refit_skip_multiplier`, default 10×)
   - **Refit zone**: In between — tries adding the face, refitting, and checking **all** accumulated faces against tolerance

3. **Best-of-seeds selection**: For each starting face `fi`, all seeds are tried. The one producing the hypothesis with the largest total face area wins.

4. **Greedy face-order iteration**: Faces are visited in index order. Once a face is claimed by any hypothesis, it's excluded from future seeds and BFS expansion.

5. **Final refit**: After BFS expansion completes, a final refit from all accumulated faces produces the definitive surface parameters.

### Key Differences from a Non-Abstracted Approach

Without this abstraction, you'd have 4-5 copies of the ~200-line BFS loop, each with inlined surface-specific logic. The traits pattern eliminates this duplication while keeping each surface type's specifics cleanly separated:

- **Seed generation** varies dramatically (1 face for planes, 3 non-mutual-neighbor faces for cones, 1-ring neighborhoods for spheres/tori)
- **Fitting** varies in complexity (weighted normal average vs. multi-step SVD+Gauss-Newton)
- **Acceptance criteria** are entirely different (face count vs. angular coverage vs. solid angle spread vs. minor-circle coverage)
- **Convexity** has different geometric meaning per type (radial from axis, radial from center, radial from tube center, or N/A)

But the BFS expansion logic, tolerance checking, refit-or-skip decisions, bootstrapping, best-candidate tracking, and hypothesis commitment are **identical** across all types — exactly the code that would be error-prone to duplicate.

Normal-line intersections between adjacent faces on a torus produce a **mix** of tube curvature ($\approx r$, from edges running along the tube) and azimuthal curvature ($\approx R - r$ for concave, $\approx R + r$ for convex, from edges running along the major circle). The tube-curvature estimates are the **smallest** values. Using the median picks a value contaminated by azimuthal curvature ($\approx 6$ instead of the true $r = 1.5$ for the filleted_pipe inner fillet). The 25th percentile consistently selects the correct tube-curvature cluster. This was the key fix for detecting the z=28.5 inner concave fillet (R=7.5, r=1.5).

### Torus seeding: face-based 1-ring neighborhoods

Component-based seeding fails for tori because connected components typically contain cylinder body faces and fillet faces mixed together (e.g., a 383-face component). Face-based seeding works: for each uncommitted candidate face, build a seed consisting of that face plus all faces sharing at least one vertex (the 1-ring vertex neighborhood). Only uncommitted faces are included. Seeds with <7 faces or <9 vertices are skipped. BFS naturally skips faces already committed to a toroidal hypothesis, so later seeds avoid already-identified regions. This is simpler and more robust than vertex-neighborhood seeding with post-merge: every toroidal face gets a chance to anchor a hypothesis without needing merge to combine overlapping seeds.
